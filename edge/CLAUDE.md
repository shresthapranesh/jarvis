# edge/ — the jarvis server, in Rust

Read `README.md` here before changing the API, runs, the agent loop or a test hook — it has the wire-format contracts and what each module ports.

- Goal: jarvis on old, low-RAM hardware. This is the whole server and CLI; only the agent's notebook kernels run Python (`tools/`: the `jarvis` SDK, web and browser). The name is historical — it began as an edge in front of the Python server. Module docs that say "a port of `core/…`" name Python code that is gone; the behaviour they describe is this code's now.
- It owns :8000: GraphQL (`graphql.rs`, `gql/`; Strawberry's 400s in its words, introspection on), subscriptions, REST (`rest.rs`, `logs.rs`), `/ws/browser`, `/health`, and the SPA from `$JARVIS_APP_DIR/static/dist` (`web.rs`). `frontend/schema.graphql` is exported from it (`pnpm schema` → `--print-schema`).
- **The schema** (`src/schema.rs`): `schema.sql` makes a new database, `migrate` brings an older one up, at start and before CLI commands. A change goes in both; `tests/test_edge_schema.py` checks a migrated database has the fresh shape, and holds both to what Python made of them when the schema moved here (recorded — update the recording with the change).
- **Tests** (`tests/test_edge_*.py`) compare the binary with what Python answered, recorded before Python's server and runtime were deleted (`tests/python_golden.py`, `tests/golden/python/`). A deliberate change to an answer is an edit to the recording, said in the commit. Databases are seeded with `tests/seed.py`. `cargo test` runs the unit tests and the Rust integration tests (`edge/tests/*.rs`), where new server tests go: they drive the built binary over a throwaway `WORK_DIR` against a scripted fake Ollama (`edge/tests/support/mod.rs`: `Edge`, `FakeModel`) — no Python.
- **Runs** (`runs.rs`, `gql/start.rs`, `gql/runs.rs`): a trigger writes the rows + `jobs` row, registers the run *before* the commit, then wakes the agent loop. Stops set the run's flag and the job's `cancel_requested`. `JARVIS_RUN_JOBS=0` queues without running (tests).
- **Agent loop** (`src/agent/`): claims every chat, automation, board-task and workflow job (`queue.rs`, Python's claim under the thread lease; legacy `runtime` values ignored). A sub-agent's conversation (`surface = 'subagent'`, `parent_id`) gets `subagent` jobs instead of `chat` ones (`gql/start.rs:enqueue_turn`): a chat turn with the one sub-agent prompt and toolset (`workers::SUBAGENT_PROMPT`, `Kind::Subagent` — no roles; the task says what to do), claimed under its own slots so a turn waiting on its sub-agents can't starve them. An agent spawns and re-uses them with `run_agents` (`turn.rs`; `gql/start.rs:spawn_subagent` / `task_subagent`): with `wait` it waits on their runs and reads their Message rows, without it their answers come back as `source = 'subagent:<id>'` messages (`deliver_to_parent`) that join the parent's run or start its next turn; `check_agents` reads where they stand; a stopped run stops the turns its agent started. Only a web chat may skip the wait (an automation, a board task or a bot's chat can't be told later). A turn claimed again after a restart answers its open `run_agents` call from the sub-agent turns it had started (`resume_agents`); a run with no conversation deletes its sub-agents as it ends, and `sweep.rs` those a crash left. Over GraphQL: `Conversation.subagents` / `parent`, `Message.source`, a `SubagentEvent` on the parent's run when one changes, and `deleteConversation` takes a conversation's sub-agents with it (`gql/conversation.rs`). Tested in `tests/test_edge_subagent.py`. Any conversation's agent can also write to another conversation — `sendToConversation` (`gql/start.rs`, the SDK's `jarvis.send_message`; the sender is `X-Jarvis-Conversation`): a `source = 'conversation:<sender id>'` message under a `[Message from conversation <id> (<title>)]` line, which joins the run going there or starts that conversation's next turn (`deliver_sourced`, shared with `deliver_to_parent`); one-way, nothing returns to the sender (`edge/tests/send.rs`). An automation's agent run and a workflow's agent node answer in a conversation too, kept out of the sidebar by its surface (`conversations` lists `web` by default): a prompt run's own `automation_<run id>` (a stateful automation's or monitor's shared `automation_<automation id>`, as before), `surface = 'automation'`, the reply's id the run's so its steps are rows of it (`automation::begin_conversation`, `AutomationRun.conversationId`); and one per agent a workflow node runs, `surface = 'workflow'`, `spawned_by` the run, titled `<workflow> · <node>`, its reply a `chat` run of its own on that conversation with no job behind it (`Registry::register_unqueued`, which `sweep_pending` leaves alone), so the conversation's page follows it live as a chat turn — text, steps, a stop, a message sent meanwhile, which becomes the next turn — and its history written as the conversation's thread when it ends (`workflow/agent.rs:Seat`, `WorkflowRun.conversations`) — only in a workflow's own run, not a child workflow's or `main.py run`'s. Either can be opened and gone on with as a chat; they are deleted with their automation or workflow (`edge/tests/run_conversations.rs`). The turn (`turn.rs`) — prompt as `model_request_node` built it (`prompt.rs`; the static system prompt is `src/system_prompt.md`, compiled in), `run_cell`, the todo tools, `remember`, `write_artifact`, `run_agents`/`check_agents`, bound MCP tools, `run_workflow`; a workflow's agent node still has the in-memory `spawn_workers` (`workers.rs`, a port of `tools/workers.py`; its workers share the sub-agent prompt and toolset — no roles; workers' tools in `files.rs`/`artifacts.rs`, ports of `tools/files.py`/`tools/artifacts.py`). Bad tool arguments are answered for the model as `invoke_tool` worded Pydantic's errors (`tools::Args`, shared with the workers). A failure short of an answer is the model's to read too, in a chat, automation, board or sub-agent turn (`turn.rs`, not the workflow agent node or its workers): a tool that fails on the server's side is an error result (three in a row fail the run), a reply cut off at the output limit is asked for again in smaller pieces (two in a row fail it), and a run out of budget — warned in its turn context at 80% — gets one closing reply with no tools run. The budget (`budget.rs`) is such a turn's only ceiling — no step limit beside it: its clock stops while the turn waits on a person's answer or approval or on its sub-agents (`Budget::waited`), and a turn claimed again after a restart goes on from what its thread shows it had spent (`Turn::spent`). A job claimed more than its `max_attempts` (3) times — each claim after the first follows a restart — is failed, not run again (`Agent::serve`). Three tool batches in a row with the same calls and the same results get a note appended to the last result saying so (`Turn::repeats` — a count, not a judge). The volatile tail opens with today's date in the scheduler's zone (`prompt::today`), and a sub-agent's context is its prompt, its project's instructions and the date (`prompt::for_subagent`) (`edge/tests/limits.rs`). Retrieval and embeddings (`retrieve.rs`/`embed.rs`, ports of `core/retrieval.py`, `search_memory`, `search_skills`, `search_episodes`, `upsert_memory`), summarizing and episodes (`summarize.rs` + `llm/compact.rs`), events/steps as `core/streaming.py` made them (`events.rs`), automations (`automation.rs`), board tasks (`board.rs`) with notifications (`src/notify.rs`), workflows (`workflow/`). A model it can't call, a prompt it can't build, or a run that can't start (`Agent::fail_start`) fails the run with the reason. At start, `recover` + `sweep.rs` (Python's startup sweeps; `--startup-sweep` runs just that). Tested in `tests/test_edge_agent.py` and `tests/test_edge_loop.py`.
- **Approvals** (`src/approvals.rs`, a port of `core/tool_gate.py` + `core/approval.py`): gated tools wait on their `approvals` row, answered by `resolveApproval` (`src/gql/approval.rs`), which also runs approved deferred actions. An agent's (`X-Jarvis-Caller: agent`) `deleteWorkflow` / `deleteSkill` / `deleteAutomation` / `callMcpTool` goes through `approval::gate_action` when `approval.required_actions` names it: recorded, an open duplicate reused, the mutation failing with "Approval required: …".
- **The board** (`src/gql/board_view.rs`, the `board` query): every top-level chat and board task in the column of what it is doing — `todo`, `working`, `needs_me`, `blocked`, `done` (cut to `doneLimit`, 20). A task takes its column from `board_tasks.status`; a chat from its live run, the questions open on it and how its last reply ended. `board_tasks` is the record behind a task's conversation (`boardtask_<id>`, `Conversation.boardTask`), not a second kind of thing; `boardTasks` stays for the SDK. Tested in `edge/tests/board_view.rs`.
- `src/budget.rs` ports `core/budget.py`. Trackers return the events; the caller emits them.
- **Writes** (`src/gql/*`): ports of the Python resolvers and `db/ops.py` CRUD — board, conversations, automations (schedules validated by `cron.rs`, the scheduler told to reload), settings (`settings.rs`: `KNOWN_SETTINGS`, `validate`, `redact`; an `mcp.*` key reconnects the MCP servers), models and endpoints (`models.rs`), tool policy (`tools.rs`; the SDK catalogue is `src/gql/sdk_tools.json`, exported from `tools/sdk.py` — `JARVIS_UPDATE_GOLDEN=1 uv run pytest tests/test_edge_parity.py -k catalogue`), memory and skills (`searchMemory` is the SDK's `search_memory`). Errors Python's parsers worded are worded here, with the reason. Diffed in `tests/test_edge_parity.py`.
- **`modelSync`** is `src/discovery.rs` (a port of `core/model_discovery.py`) with Bedrock's SigV4 and credential chain in `src/aws.rs`. A listing it can't read skips that provider with the reason; diffed in `tests/test_edge_model_sync.py`.
- **Scheduler** (`schedule.rs`): every timer. `src/cron.rs` ports APScheduler's `CronTrigger` (DST quirks included), held to its recorded answers in `tests/test_edge_schedule.py`. `schedule.rs:dispatch` is a port of `dispatch_board_tasks`.
- **Memory consolidation** (`src/consolidate/`): ports of `core/memory_consolidation.py`, `core/project_memory_consolidation.py` and `tools/text_dedupe.py` (which the SDK still uses — change both). `--maintenance-run <task>` runs one sweep; compared with Python's recorded sweeps in `tests/test_edge_loop.py`.
- **LLM layer** (`src/llm/`): hand-written clients for Anthropic, Bedrock, Gemini, Ollama, Chat Completions (OpenRouter, endpoints) and Responses (Meta). `shape.rs` ports `core/messages.py` + `core/context_cache.py`, `compact.rs` `apply_per_call_compaction`, `perf.rs` `core/perf.py`; `transcript.rs` is the v1 record (`edge/transcript_format.md`). `--llm-shape` / `--llm-call` drive it alone; compared with LangChain's recorded requests and replies in `tests/test_edge_llm.py`.
- **Kernels** (`src/kernels/`): `ipykernel` processes over the Jupyter wire protocol (pure-Rust `zeromq`, ipc). A port of `core/kernels.py`; `--kernel-cells` drives them for `tests/test_edge_kernels.py`. The preload is `tools/preload.py` (cheap modules only — pandas & co. are the agent's to import; bound lazily, the first traceback's `inspect.getmodule` loads them anyway). Output past 30,000 characters keeps its head and tail. The PNG/JPEG images a cell shows (4 a cell, 1.5 MB each) go to the model after the text of a chat, automation, board or sub-agent turn's `run_cell` result as image parts, their bytes `transcript_blobs` rows (`turn.rs:run_cell`), when `llm::sees_tool_images` (Claude, Gemini, an Ollama model listing `vision`) and the call has room (`image_room`: 20 images / 10 MB in the view `per_call_for` leaves — a collapsed tool group takes its images with it; an append-only history keeps all of them). Otherwise, and for the workflow agent node, workers and `--kernel-cells`, an image is a line of the text; a thread moved to a model that can't take them is sent lines (`shape::unseen_tool_images`). Tested in `edge/tests/images.rs`. A cell's time is `run_cell`'s `timeout` (default 60 s, held to 1–600, `tools::Args::cell_timeout`); one timed out is told it can ask for more or use `jarvis.start_job`, and a stopped run drops its cell, which interrupts it (`Busy`). At most `JARVIS_MAX_KERNELS` (12) kernels; one untouched for `JARVIS_KERNEL_IDLE_TIMEOUT` seconds (1800) is shut down, a sub-agent's (`surface = 'subagent'`, no job pending or running on it) after `JARVIS_SUBAGENT_KERNEL_IDLE_TIMEOUT` (300) — never one with a cell in it or waiting (`InUse`). The first cell in a kernel started again after cells ran in its last one (reaped, evicted, dead) is told its variables are gone; one shut down with its conversation isn't remembered. `tests/test_edge_kernels.py` strips these notes before comparing with Python; tested in `edge/tests/cells.rs`.
- **MCP** (`src/mcp/`): our own client over stdio / Streamable HTTP / HTTP+SSE / websocket, the manager, the GraphQL API (`src/gql/mcp.rs`), `always` tools bound in the loop. A port of `core/mcp.py` + the adapter; tested against real servers in `tests/test_edge_mcp.py`. OAuth sign-in (`mcp/oauth.rs`, the `mcp_oauth` table — never exposed by a query): the manager puts the token on each connection, renewing it when expired or refused.
- **Browser** (`src/browser/`): `/ws/browser`, the live view (a port of `core/browser_stream.py` + `routes_browser.py` + `ensure_running`); tested against a fake DevTools browser in `tests/test_edge_browser.py`.
- **Bots** (`src/bots/`): Telegram and Discord; a message is `start_chat`, the reply follows the run. Tested against a fake chat service and the loop's fake model in `tests/test_edge_bots.py`.
- **Command line** (`src/cli/`): `jarvis-edge run|config|model|start` (no command serves) — a port of `main.py`, compared with its recorded output in `tests/test_edge_cli.py`. `mcp add|list|get|remove|login|logout` is the edge's own (`cli/mcp.rs`, `tests/test_edge_cli_mcp.py`): it writes `mcp.servers` as the MCP tab does, prints header/env values as `••••`, and tells a running server to reconnect; `login` runs the OAuth flow with a loopback redirect (or a pasted address), tested against `tests/fixtures/oauth_mcp_server.py`.
- `src/catalog.rs` compiles in `src/builtin_models.json` (the first entry is the default model) — rebuild after editing it.
